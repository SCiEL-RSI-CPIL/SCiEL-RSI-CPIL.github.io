<Sec id="idea" />

We use *recursive self-improvement* (RSI) for a process in which the improvements a system makes <span class="key">strengthen its capacity for further improvement</span>: the system gets better at getting better <a class="cite" href="#ref-14">(Yampolskiy, 2015)</a>. Here “the system” includes its procedures and inherited methods; the underlying language model may or may not stay fixed.

We approach this through cumulative culture. In people and organisations, experience persists in practices, routines and artifacts <a class="cite" href="#ref-15">(Henrich, 2016;</a> <a class="cite" href="#ref-16">Levitt and March, 1988)</a>; earlier instrument designs inform later ones <a class="cite" href="#ref-17">(Nersessian, 2009)</a>; existing technologies, and the know-how to combine them, support further invention <a class="cite" href="#ref-18">(Arthur, 2007)</a>; and what is inherited can strengthen the very capacity to build on it <a class="cite" href="#ref-19">(Mesoudi and Thornton, 2018)</a>. <span class="key">SCiEL turns this loop between inheritance and innovation into a way to search.</span>

<div class="box prose">
  <p class="label">Terms used throughout</p>
  <dl>
    <dt>Deme</dt>
    <dd>A subpopulation of programs that evolves on its own, with its own lineages. A run has several; most runs here have eight. (The code and the run viewer call them islands.)</dd>
    <dt>Research cell</dt>
    <dd>A standing question a deme keeps open. It plans experiments, writes and runs its own tools, and draws conclusions.</dd>
    <dt>Finding</dt>
    <dd>A conclusion from a research cell, with its measured effect. Findings are what travels between demes.</dd>
    <dt>Culture</dt>
    <dd>Everything the population has learned and can pass on: findings, tools, and the policy and world model that steer the search.</dd>
    <dt>World model</dt>
    <dd>A learned forecast of whether a proposed edit will pay off, used to screen proposals before they cost an evaluation.</dd>
    <dt>Frontier</dt>
    <dd>The best scores reached so far. An edit “at the frontier” starts from a parent close to the run's best.</dd>
    <dt>π</dt>
    <dd>The share of the model's edits that beat their parent: the slope of the task as the model sees it. Differences smaller than the task's noise level ε do not count.</dd>
  </dl>
</div>

Five ideas carry the design:

1. **The procedures improve along with the programs.** An improvement is recursive when it strengthens the capacity for the next one. SCiEL keeps what it learned while searching, and exports it to the next run.
2. **Culture passes on only after a trial at the recipient.** A skill outlives the person who found it because it is taught, tried by the learner, and dropped when it fails. In SCiEL a hypothesis is tested as an experiment; what holds becomes a finding or a tool; it is delivered to other demes and kept only if the recipient's own trial confirms it.
3. **What the population learned shapes how it grows.** Crossing merges lineages that each solved part of the task; stalled demes restart where the world model sees unexplored promise; new demes start from a varied set of approaches, so an idea can survive long enough to pay off.
4. **Every self-modification is an experiment.** Every choice (which deme, which parent, which kind of edit, when to open research) is drawn at random from a logged distribution. So the system can estimate from its own logs, without bias, whether a change to itself helped before it keeps it.
5. **The landscape belongs to the model.** How hard a task is depends on π, how often the model's edit beats its parent. Culture changes what the model sees, so it changes π. That is the lever recursive improvement pulls, and it can be measured.

We study SCiEL in the [Empira arena](https://research-arena.small-pine-3af7.workers.dev/experiments), an independent benchmark of research tasks for self-improving systems, with an open 27B model served locally, both <span class="key">with its weights frozen and with LoRA adapters trained during the run</span>.

<Sec id="why" />

A hard problem is a long climb that the model sees one edit at a time. Most edits go down, some produce invalid solutions, and small local bumps stop a greedy climber. A single model sampled many times never chains steps. A single climber chains them but stops at the first bump. A swarm splits the budget, and its members never learn from each other.

<span class="key">SCiEL is built for the climb.</span> Demes explore in parallel, a policy learns which moves pay, a world model screens edits before they cost an evaluation, and culture moves what one deme learned to the others. The toy landscape below shows the difference.

### A world model of the search

Before the language model is called, SCiEL forecasts whether a proposed step will raise its lineage's best score. It does not model the task; it models the search itself, from the parent, the deme, the kind of edit, an embedding of the code and the run's history so far. It starts from a model pretrained on tabular data, so it is useful after a few dozen steps, and refines itself on the run's own steps; steps inherited from earlier runs give it a head start.

Like every learned part of SCiEL, <span class="key">it acts only while it earns it</span>: at each refit it must beat the base rate and simple per-group averages on steps it was not fitted to, or it is held back.

<WorldModelLoop />

### Where the long shots live

A guess that lands somewhere new is usually worse than the current best at first. If the population kept only the best, it would be thrown out before anyone could build on it. So each deme keeps a map of niches (groups of programs whose code is alike) with one best program per niche, and <span class="key">a newcomer competes only within its own niche</span>. <span id="s-niche"></span>

### Generations, and the second order

The runs so far are one generation. Two predictions come next. **First order:** a generation that inherits the tested repertoire of the last one should improve faster than one that starts from scratch. **Second order:** the procedures that create culture (when to open research, how to share, what to keep) should themselves improve across generations.

We will run the same tasks over generations 1 → 2 → 3, each starting from what the previous one exported, against matched runs from scratch at equal cost, and report evaluations to reach a threshold and π at the frontier by generation; for the second order, each generation's procedures against the last.</p>

<Sec id="weights" />

Everything above leaves the model untouched: culture lives in the prompts, tools and policies around it. The deepest place to keep culture is the model itself. DeltaServe <a class="cite" href="#ref-13">[13]</a> trains and serves LoRA adapters (small sets of extra weights that adjust a model without retraining it) inside the same inference engine on one GPU, swapping them in by name, so a run can learn while it searches.

Training a model on its own search usually goes wrong in one of two ways: it learns from its own samples and collapses onto a few programs, or it learns from wins that were only noise. SCiEL is built to supply better data:

- <span class="key">Every step comes with a logged probability</span>, so the training set can be reweighted for the policy that produced it, as in off-policy reinforcement learning.
- The world model marks which transitions were genuinely informative.
- Niches and demes keep many kinds of program alive over long runs, so the adapter sees many routes to the frontier instead of one.
- The data is transitions from a weaker parent to a stronger child that held up when re-measured, not just the best programs.

<span class="key">An adapter does not replace the generator.</span> It is one more randomised option, adopted only through the same trial at the recipient as any other piece of culture, so the base model keeps proposing and its diversity is kept. This line of work is under way and will be reported separately.

<Sec id="use" />

SCiEL pays off on a particular kind of task, and whether yours is one can be checked before any compute is spent. It fits when three things are true:

1. **You can check an answer you can trust:** exactly, like arithmetic or a replay, or on data the search never saw, like held-out days.
2. **The best known answer can still be beaten:** there is room above it, and that room is larger than the noise in your score.
3. **Progress hides behind rare long shots:** most tries fail, and the ones that matter are bold guesses a single attempt would never risk. <span class="key">SCiEL makes long shots affordable</span>: a population holds them, niches keep odd ones alive, the world model screens them before they cost an evaluation, the policy learns which kinds pay, and culture spreads the rare hit.

Poor fits are puzzles solved in one shot, tasks already at their ceiling, and anything without a score you would bet on.

<details class="box prose">
  <summary><b>The precise conditions</b></summary>
  <p>The checker is exact or survives probes for leaks; the headroom above the best reference exceeds 4ε, four times the noise level; and the upper bound of π at the frontier is at least 5/B, where B is the evaluation budget, so the run can expect several improvements before the budget runs out.</p>
  <p>Formally, a task is ⟨X, F, h, h<sup>*</sup>, M, B⟩: the candidates the model writes, the set of valid solutions, the objective the run sees and the true one, the model's edit operator, and the budget. Because the landscape is defined by the model's edits, it moves as culture changes what the model sees.</p>
</details>

Not sure? Point `sciel task` at a folder of materials. It drafts the task, checks all three conditions before any compute is spent, and repairs what it can. See also the [quick start on GitHub](https://github.com/Doldrums/sciel#quick-start).
